# SRS v1.0 — Software Requirements Specification: SmartDesk ITSM API

## 1. Вступ

### 1.1 Мета документа

Цей документ описує специфікацію вимог до програмного забезпечення (Software Requirements Specification, SRS) системи **SmartDesk ITSM API**. Метою документа є чітка формалізація функціональних, нефункціональних вимог, системних обмежень та зовнішніх інтерфейсів для використання під час розробки, тестування та здачі проєкту в межах курсу «Моделі життєвого циклу, принципи і методології розробки ПЗ».

### 1.2 Сфера застосування (Scope)

SmartDesk є REST API сервісом для управління IT-інцидентами (Helpdesk / Service Desk), який розв'язує дві ключові проблеми:

1. Запобігання «голодуванню» низькопріоритетних задач у черзі за допомогою динамічного розрахунку терміновості (Dynamic Urgency) за дедлайнами SLA.
2. Скорочення часу на вирішення повторюваних інцидентів за допомогою семантичного векторного пошуку аналогів у базі знань (Sentence Embeddings + Cosine Similarity).

### 1.3 Терміни, скорочення та абревіатури

- **ITSM / ITIL:** IT Service Management / Information Technology Infrastructure Library — методології управління IT-послугами.
- **SLA:** Service Level Agreement — угода про рівень обслуговування (нормативний час вирішення інциденту).
- **Embedding:** Багатовимірний векторний масив дійсних чисел, що відображає семантичний зміст тексту.
- **Cosine Similarity:** Метрика обчислення кута між векторами в багатовимірному просторі для оцінки близькості тексту.
- **DTO:** Data Transfer Object — об'єкт для валідації та передачі даних між шарами системи.

## 2. Загальний опис системи

### 2.1 Перспектива продукту

SmartDesk розробляється за концепцією **API-First** з трирівневою архітектурою (Presentation -> Business Logic -> Data Access). Сервіс функціонує як автономний REST API бекенд, що надає інтерактивну OpenAPI/Swagger UI документацію та інтегрується з базою даних SQLite.

### 2.2 Класи користувачів та характеристики

1. **Співробітник компанії (Кінцевий користувач):**
   - Створює нові тікети про технічні проблеми.
   - Отримує семантичні рекомендації схожих вирішених інцидентів із готовими кроками розв'язання.
   - Оновлює або видаляє власні звернення за потреби.
2. **Інженер технічної підтримки (Support Engineer):**
   - Переглядає смарт-чергу інцидентів, відсортовану за динамічним індексом терміновості.
   - Змінює статуси тікетів (`Open` -> `In Progress` -> `Closed`).
   - Доповнює базу знань успішними резолюціями.
3. **Адміністратор системи:**
   - Моніторить цілісність бази даних, проводити очищення та адміністрування категорій.

### 2.3 Операційне середовище

- **Мова програмування:** Python 3.10+
- **Фреймворк:** FastAPI, Uvicorn
- **База даних:** SQLite3 + SQLAlchemy 2.0 ORM
- **ML/NLP Бібліотека:** `sentence-transformers` (модель `all-MiniLM-L6-v2`)
- **Валідація та тестування:** Pydantic V2, Pytest

## 3. Специфічні вимоги

### 3.1 Функціональні вимоги (Functional Requirements)

- **FR-01 (Створення інциденту):** Система повинна приймати HTTP POST запит на `/tickets/` з полями `title`, `description`, `category`, `priority` (1–4) та `sla_hours` і зберігати запис у БД зі статусом `Open`.
- **FR-02 (Семантична векторизація):** При створенні або оновленні тексту тікета система повинна автоматично генерувати 384-вимірний L2-нормалізований вектор та зберігати його у форматі JSON в базі даних.
- **FR-03 (Динамічна смарт-черга):** На запит `GET /tickets/queue` система повинна розраховувати показник Dynamic Urgency для всіх відкритих тікетів на основі пріоритету, простроченого часу та категорії (застосовуючи відповідну математичну формулу) та повертати відсортований список за спаданням.
- **FR-04 (Інтелектуальний пошук аналогів):** На запит `GET /tickets/{id}/similar` система повинна обчислювати косинусну близькість між вектором поточного тікета та закритими тікетами цієї ж категорії, повертаючи топ-3 релевантних результатів із коефіцієнтом схожості $\ge 0.35$.
- **FR-05 (Повний CRUD та життєвий цикл):**
  - `PUT /tickets/{id}` — оновлення атрибутів тікета з автоматичною реіндексацією ембеддингу при зміні тексту.
  - `PATCH /tickets/{id}/status` — зміна стану заявки (`Open`, `In Progress`, `Closed`).
  - `DELETE /tickets/{id}` — видалення запису з бази даних з поверненням коду `204 No Content`.

### 3.2 Нефункціональні вимоги (Non-Functional Requirements)

- **NFR-01 (Швидкодія):** Час формування смарт-черги та семантичного пошуку для бази обсягом до 500 активних записів не повинен перевищувати 300 мс на стандартному CPU.
- **NFR-02 (Цілісність та персистентність):** Збереження даних повинно виконуватися у реляційній СУБД SQLite із дотриманням ACID-транзакційності.
- **NFR-03 (Модульність та SOLID):** Код має відповідати трирівневій архітектурі, розділяючи роутери, сервіси та репозиторії. Впроваджені патерни Repository та Strategy.
- **NFR-04 (Валідація та помилки):** Усі вхідні дані мають валідуватися через Pydantic. При невалідних даних повертається HTTP 422, при відсутності запису — HTTP 404.
- **NFR-05 (Якість коду та покриття):** 100% проходження 7 автоматизованих тестів у Pytest, що покривають математику Strategy, косинусну схожість, сортування черги та DTO-валідацію.

### 3.3 Зовнішні інтерфейси

- **OpenAPI / Swagger UI:** Автоматично згенерована інтерактивна документація за адресою `/docs`.
- **JSON REST API:** Стандартизований формат обміну даними.

## 4. Сценарії використання (Use Cases & Diagram)

Основними акторами системи є **Співробітник (Employee)** та **Інженер підтримки (Support Engineer)**.

- **Співробітник:** `Створити тікет`, `Отримати схожі рішення`, `Редагувати тікет`.
- **Інженер підтримки:** `Переглянути смарт-чергу`, `Змінити статус тікета`, `Додати резолюцію / Закрити тікет`.
- **Адміністратор:** `Видалити тікет`.
